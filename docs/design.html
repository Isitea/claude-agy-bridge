MCP 서버 설계 · claude-agy-bridge

Claude가 구현하고, Antigravity가 검증한다

계산과학 코드를 작성하는 Claude Code 세션이 도구 호출 한 번으로 Antigravity에게 물리·수치·유도 검증을 요청하는 MCP 서버. 완성 후 별도 저장소에 이식되는 것을 전제로 설계했다.

상태 설계 확정 · Phase 0 착수 전 런타임 Python 3.14 + uv 계약면 CLI 서브프로세스 개정 2026-08-07
01

무엇을 만드는가

Claude Code는 구현을 맡고, Antigravity는 읽기 전용 자문·검증자로 붙는다. API 키를 새로 관리하지 않기 위해, 두 CLI가 이미 OAuth 인증되어 있다는 사실을 그대로 이용한다. 계약면은 API가 아니라 agy 서브프로세스다.

설계를 지배하는 전제가 하나 있다. 이 저장소는 도구를 만드는 곳이고, 실제 사용은 다른 세션·다른 저장소에서 일어난다. 따라서 브리지는 자신의 설치 경로 밖 어떤 경로도 하드코딩하지 않으며, 이 설계 대화를 보지 못한 세션이 문서만 읽고 쓸 수 있어야 한다.

범위 안
과학적 자문 · 구조화된 검증 판정 · 맥락 유지 왕복 · 임의 저장소로의 이식
범위 밖
agy의 파일 수정 · 역방향 브리지(agy → claude) · API 직접 호출 · Node.js
02

실측이 설계를 바꾼 지점

아래 값은 추정이 아니라 이 머신에서 agy를 직접 실행해 얻었다. 실측 표시가 붙은 것은 확인된 사실이고, 나머지는 그 위에 세운 설계 판단이다.

확인 항목결과설계 영향
--output-format json {conversation_id, status, response, duration_seconds, usage} 반환 파싱 계약 확정
--conversation <id> 맥락 유지 확인. 재개 시 캐시 히트 12,206 토큰 세션 재사용이 저렴
--json-schema structured_output에 파싱된 객체로 반환 판정 스키마 강제 가능
콜드스타트 총 13.6초 중 추론 2.9초 → 프로세스 오버헤드 약 10초 드물고 굵게 묻기
기본 입력 토큰 호출당 약 17k (agy 자체 시스템 프롬프트) 일일 호출 상한 도입
모든 행은 실행 결과에서 직접 옮겼다. 모델은 검증의 독립성을 위해 gemini-3.1-pro-high로 고정한다 — agy를 통해 Claude 모델을 부르면 "다른 관점의 검증"이라는 목적이 훼손된다.

함정 A 성공을 가장한 침묵

헤드리스 agy는 파일 읽기 도구에 권한이 필요하면 프롬프트를 띄울 수 없어 자동 거부한다. 이때 stderr에는 안내가 나오지만, stdout의 JSON은 이렇게 온다: 

stderr: jetski: no output produced — a tool required the "command" permission…
stdout: {"conversation_id":"…", "status":"SUCCESS", "response":"", …}

status는 SUCCESS인데 응답은 비어 있다. 이것을 통과로 오독하면 검증받지 않은 코드가 검증된 것처럼 통과한다. 이 시스템에서 가능한 최악의 버그다. → 브리지는 빈 response를 오류로 승격하고 stderr를 그대로 전달한다. Phase 1의 최우선 회귀 테스트가 기능이 아니라 이 실패 모드인 이유다.

함정 B 커스터마이즈 탐색이 CWD에 묶여 있다

agy는 .agents/skills/와 AGENTS.md를 CWD에서 저장소 루트까지 거슬러 올라가며 찾는다. 본 저장소에 과학 스킬을 두면 대상 프로젝트에서는 로드되지 않는다. 반대로 대상 저장소를 CWD로 삼으면 그쪽 AGENTS.md(대개 구현자용 지시)를 상속해 검토자 역할과 충돌한다. → 스킬 파일 배치를 포기하고 프롬프트 주입 방식으로 간다(§05).

03

아키텍처

두 프로세스는 같은 파일시스템 위에 있다. 그런데 함정 A 때문에 agy에게 파일을 읽히는 경로는 기본값이 될 수 없다. 그래서 브리지가 파일을 읽어 프롬프트에 인라이닝한다 — agy 쪽에 아무 권한 설정도 요구하지 않고, 결정론적이다. 다만 이 경로에는 실측으로 확인된 128 KiB 천장이 있고, 그 위로는 다른 길이 필요하다 (§05).

04

브리지는 판단하지 않는다

MCP 서버 안에는 LLM이 없다. 브리지는 전적으로 기계적으로 동작한다 — 모델을 호출하지 않고, 요약하지 않고, 무엇이 중요한지 고르지 않는다. 지능은 양 끝단에만 있다.

단계주체성격
무엇을 언제 물을지 결정 — mode·files·question 작성Claude판단
설정 해석, 파일 읽기, 플레이북 선택, 프롬프트 조립브리지결정론적 코드
서브프로세스 실행, JSON 파싱, job·세션 상태 관리브리지결정론적 코드
과학적 판단agy · Gemini판단
판정을 받아 코드에 반영Claude판단
브리지 안의 모든 "선택"은 테이블 조회이거나 설정값이다. mode → 플레이북 매핑은 정적 사전이고, 어떤 파일이 중요한지 고르는 일은 이미 코드베이스를 들고 있는 Claude의 몫이다.

의도적인 선택이며, 이유는 셋이다.

  • 테스트 가능해진다. 함정 A에 대한 회귀 테스트가 성립하는 것은 브리지가 코드이기 때문이다. 중간에 모델이 있으면 그 경계는 결정론적으로 검증할 수 없다.
  • 세 번째 의견이 끼어들지 않는다. 중간 모델이 요약·선별하면 검증자에게 닿는 내용이 왜곡되고, 하필 문제가 있는 줄이 요약 과정에서 사라질 수 있다.
  • 비용이 0에 수렴한다. 브리지는 토큰을 쓰지 않고 수 밀리초를 쓴다.

브리지는 번역기이자 배관이다. 판단은 하지 않는다.

05

컨텍스트는 실제로 얼마나 들어가는가

"파일을 읽어 프롬프트에 넣는다"는 방식에는 천장이 있다. 추측하지 않고 재 봤다. 그리고 그 천장이 생각보다 낮은 곳에 있었다.

함정 D argv 단일 인자 128 KiB 하드 리밋

agy -p는 stdin을 읽지 않는다. 프롬프트를 argv 값으로만 받으므로 Linux의 MAX_ARG_STRLEN에 그대로 걸린다. 경계를 이분 탐색으로 확인했다.

프롬프트 크기결과
131,000 BOK
131,072 BE2BIG — Argument list too long
1,287,507 BE2BIG — 프로세스가 뜨지도 못함

getconf ARG_MAX가 2 MB인 것과는 무관하다. 그건 인자 전체 합이고, 단일 인자는 128 KiB로 따로 제한된다. 흔히 혼동되는 지점이다.

실측 로컬 HTTP fetch는 권한 없이 통과한다

파일 읽기 도구는 자동 거부되는데(함정 A), 루프백 URL fetch는 헤드리스에서 그대로 동작한다. 이 비대칭이 대용량 컨텍스트 문제를 푸는 열쇠다.

서빙 크기표식 배치회수
60 KB85% 깊이 1개성공
600 KB10 · 50 · 95% 깊이 3개3 / 3
400 KB개수 미고지 6개6 / 6

정정 "검색만 한다"는 첫 판단은 틀렸다

위 결과에서 입력 토큰이 낮다는 이유로 전문이 읽히지 않는다고 판단했으나, 오판이었다. 공통 부분문자열이 전혀 없는 래퍼로 감싼 인공 단어 8개를 균등 분포시켜 리터럴 검색을 불가능하게 만든 뒤, 프로덕션 모델로 다시 측정했다.

파일 크기회수소요inputcache_read
600 KB8 / 8 — 행 번호까지 정확45.9 s41,35693,543
2 MB8 / 8100.0 s75,492448,253

낮은 input_tokens는 안 읽혔다는 뜻이 아니라, agy가 행 번호가 붙은 탐색 가능한 뷰로 파일을 여러 번 나눠 읽고 그 중간 상태가 캐시로 계상되기 때문이다 (cache_read가 크기에 비례해 증가한다). 전략 C에 커버리지 손실은 없다. 비용은 정확도가 아니라 지연으로 나타난다.

전환은 context.strategy = "auto" 하나로 처리한다 — 100 KB 이하면 A, 초과하면 C로 자동 전환하고 전환 사실을 도구 결과에 명시한다. 소비 세션은 이 결정을 알 필요가 없다.

이 정정이 설계를 하나 지웠다 — 전략 B 폐기

원래 세 번째 경로로 워크스페이스 위임(--add-dir로 저장소를 주고 agy가 스스로 탐색)을 남겨 뒀었다. C가 같은 목적을 권한 설정 없이 달성하는 것이 확인된 이상 유지할 이유가 없다. B를 지우면 permissions.allow 문법 확인, README 사전 작업 절, 설정 노브, 그리고 이 세션에서 끝내 검증하지 못한 경로가 전부 함께 사라진다. 얻는 것 없이 표면적만 넓히던 부분이었다.

전략 C는 소스를 로컬 네트워크에 여는 일이다

편리한 만큼 같은 머신의 모든 프로세스에게 열린 창구이기도 하다. 그래서 강제 요건을 둔다 — 127.0.0.1 바인딩 고정(설정으로도 변경 불가), 임의 고포트, 경로에 1회용 랜덤 토큰, 디렉터리 리스팅 금지·화이트리스트만 노출, deny_globs를 서빙 경로에도 동일 적용, GET만 허용, 서버 수명 = job 수명이며 예외·타임아웃 경로에서도 종료를 보장한다. 유휴 상태로 남은 서버가 가장 흔한 사고 원인이라 agy-bridge doctor가 잔존 여부를 점검한다.

06

도구 표면과 실행 모델

도구는 다섯 개로 제한한다. 도구가 많으면 소비 세션이 선택에 토큰을 쓰고, 실제로 필요한 동작은 묻는다 · 받는다 · 이어 묻는다 셋뿐이다.

도구역할
agy_consult자문·검증 요청. 동기 대기하다 한계를 넘으면 job 핸들 반환
agy_resultjob 결과 조회
agy_followup기존 대화를 이어 재질문 (캐시 히트로 저렴)
agy_sessions활성 세션·작업 목록 및 종료
agy_cancel실행 중 job 중단

왜 동기 호출만으로는 안 되는가

MCP 도구 호출은 Claude를 블로킹한다. 그런데 gemini-3.1-pro-high로 실제 코드 리뷰를 시키면 수 분이 걸리고, --print-timeout 기본값도 5분이다. 그래서 agy_consult는 프로세스를 분리 실행하고 wait_seconds까지만 기다린 뒤 job 핸들을 돌려준다. 도구는 하나인데 반환 형태가 둘이다.

판정은 산문이 아니라 스키마다

mode: "verify"는 --json-schema로 응답 구조를 강제한다. Claude가 곧바로 행동에 옮길 수 있어야 하기 때문이다. 

verdict     correct | minor_issues | major_issues | incorrect | insufficient_context
confidence  low | medium | high
issues[]    severity   blocker | major | minor | nit
             location   "src/thermo/from_qc.py:88"   # 파일:행 형식 요구
             problem    무엇이 틀렸는가
             evidence   물리 법칙 · 수식 · 표준 관행 근거
             suggestion 어떻게 고치는가
assumptions_made[]  검토자가 스스로 채운 가정

강조 표시된 두 필드가 이 스키마의 핵심이다

검증자가 맥락 부족을 환각으로 메우는 것이 이 구조에서 가장 흔한 실패다. insufficient_context와 assumptions_made는 "모른다"고 말할 출구를 스키마에 명시적으로 뚫어 둔 것이다. 출구가 없으면 모델은 지어낸다.

07

변화 빈도로 지식을 나눈다

함정 B 때문에 스킬 파일 배치는 쓸 수 없다. 그래서 검증 절차를 브리지가 프롬프트에 직접 주입한다. 그러면 남는 질문은 하나다 — 무엇을 브리지에 담고 무엇을 담지 않는가?

초기 설계에서는 quantum-chemistry 프로파일에 패키지별 점검 항목을 담으려 했다. 폐기했다. 그것은 적용 프로젝트마다 달라지므로 브리지에 구우면 이식성이 깨지고, 동시에 검토자 모델이 이미 아는 지식이라 인코딩할 가치도 없다. 플레이북이 적을 것은 "무엇을 확인하라"이지 "패키지 X에서 그걸 뭐라 부르는가"가 아니다.

내장 플레이북검사 항목
units-and-scales단위 정합성, 기준 상태 일관성, 분자당↔몰당, 무차원화
assumption-validity적용된 근사가 그 조건에서 유효한가 — 이상성, 조화 근사, 정상상태, 선형화
conservation-and-balance물질·에너지·전하 수지 폐합, 보존량 드리프트
uncertainty-propagation상류 오차가 하류 예측으로 증폭되는 경로, 감도 분석 필요성
numerics이산화, 수렴 기준, 강성, 조건수, 수렴성 검증 계획
derivation차원 해석, 극한·점근 거동, 경계·초기 조건 정합, 부호 규약
data-provenance계산값·문헌값·추정값의 구분, 하드코딩된 상수의 근거
어떤 계산과학 프로젝트에도 적용되는 관심사 단위 구성. 스택 이름은 한 줄도 등장하지 않는다.

중점 코드 리뷰로는 절대 잡히지 않는 실패

상류의 작은 오차가 하류에서 지수적으로 증폭되는 구조가 흔하다. 298 K에서 ΔG가 1 kcal·mol⁻¹ 어긋나면 평형상수는 약 5.4배 틀어진다 (exp(4.184 ÷ (8.314 × 298 × 10⁻³)) ≈ 5.4). 양자화학 계산의 통상 오차가 수 kcal·mol⁻¹임을 감안하면 "계산은 맞는데 예측은 무의미한" 상태에 쉽게 도달한다. 그래서 uncertainty-propagation은 오차 막대 없이 하류로 넘어가는 물리량을 지적하도록 명시한다. 이건 문법도 타입도 테스트도 잡아주지 않는다.

08

다른 저장소로 옮겨 심기

브리지는 전역 실행파일로 설치되고, 대상 저장소는 이름만 참조한다. 경로가 등장하지 않는다는 점이 요점이다. 

# 1. 설치 — 한 번
uv tool install --from /path/to/claude-agy-bridge agy-bridge

# 2. 대상 저장소에 부트스트랩
agy-bridge init --target /path/to/target-repo
  → .mcp.json 등록 · .agy-bridge.toml 생성 · 오버레이 템플릿 · 스모크 호출 1회 검증

이 설계 대화를 보지 못한 세션에게 넘기기

지식은 사람의 설명이 아니라 산출물 자체에 실려야 한다. 세 가지 매개체를 쓴다.

  • MCP 도구 설명문 — 소비 세션이 반드시 읽는 유일한 텍스트다. 비용 경고(호출당 ~10초·17k 토큰), "판정은 자문이지 사실이 아니다", running 반환 시 기다리지 말 것을 여기에 적는다.
  • README의 사전 작업 절 — agy OAuth, uv, 설치가 전부다. agy 쪽에 설정할 것이 하나도 없다 — 전략 B를 폐기하면서 권한 등록 절차가 통째로 사라졌다. 설명해야 할 사전 조건이 적을수록 다른 세션이 실패할 여지도 줄어든다.
  • agy-bridge doctor — "만든 사람에게 물어보기"를 대체하는 자가 진단. 실패 시 조치 가능한 문장으로 출력한다.

인수 조건은 하나로 못 박았다 — 새 세션이 README만 읽고 사람 개입 없이 검증 왕복 1회를 성공시킨다.

09

로드맵

모든 단계가 대상 저장소와 독립적이다. 도메인 고유 지식은 오버레이로 나중에 주입되므로 대상 프로젝트 정보를 기다릴 필요 없이 0에서 6까지 순서대로 진행한다.

PHASE 0 · 0.5d 환경 정비 mise에서 node 제거, pyproject 골격 uv run agy-bridge --help
PHASE 1 · 1d 최소 브리지 동기 agy_consult + 인라이닝 + 실패 승격 실제 코드 리뷰 1건 왕복
PHASE 2 · 1d 비동기 · 세션 job 레지스트리, 영속화, followup 5분 리뷰를 non-blocking 회수
PHASE 3 · 0.5d 구조화 판정 json-schema 연동, verify 모드 결함 샘플에서 major_issues 획득
PHASE 4 · 1.5d 과학 능력 팩 플레이북 7종 + 오버레이 발견 기구 플레이북 유무 간 품질 차이 확인
PHASE 5 · 1.5d 대용량 컨텍스트 · 운영성 전략 C 서빙 + auto 전환 + 안전 요건, 비용 계측, 호출 예산 2 MB 자료 왕복 + 서버 잔존 0
PHASE 6 · 1d 패키징 · 핸드오프 init · doctor · README · 이식성 테스트 새 세션이 README만으로 왕복 성공
